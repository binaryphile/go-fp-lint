## 10. Using fluentfp

[fluentfp](https://github.com/binaryphile/fluentfp) provides functional operations for Go slices.

### Why FluentFP Matters at Scale

This isn't about style preferences. It's about two things that define code quality:

**1. Correct by construction.** A loop has 5+ places to introduce bugs:

```go
count := 0                          // wrong initial value?
for _, t := range tickets {         // wrong collection?
    if t.CompletedTick >= cutoff {  // wrong field? wrong operator?
        count++                     // forgot to increment?
    }
}                                   // used result before loop finished?
```

The FluentFP equivalent has zero:

```go
slice.From(tickets).KeepIf(completedAfterCutoff).Len()
```

You can't forget to initialize. You can't iterate the wrong collection. You can't forget to append. The pattern either works or doesn't compile.

**2. Intent over mechanics.** Code should say *what* it does, not *how*:

```go
// Mechanics: declare, iterate, append, return
result := make([]float64, 0, len(history))
for _, s := range history {
    result = append(result, s.PercentUsed)
}
return result

// Intent: extract PercentUsed from history
return slice.From(history).ToFloat64(Snapshot.GetPercentUsed)
```

At scale, these compound. A codebase with fewer failure modes has fewer bugs. Code that reads as intent is code you can understand six months later. These aren't nice-to-haves—they're the job.

### When to Use fluentfp

| Use fluentfp when... | Use raw loops when... |
|----------------------|----------------------|
| Transforming entire collections | Early exit on first match |
| Filtering with clear predicates | Accumulating into maps (except `ToSet`) |
| Chaining operations readably | Profiled bottleneck slowing the drumbeat |
| Building membership sets (`ToSet`) | Index access needed mid-loop |
| Method references available | Generators with probabilistic logic |
